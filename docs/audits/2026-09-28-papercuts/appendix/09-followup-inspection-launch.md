# Followup/resume and run inspection/launch semantics (F9)

## Bottom line
Most of this family's oldest pain is already fixed on main: the Codex `--cd` and `--color` flags after `resume`, the silent `runs` truncation and empty-Registry traps, stale bare-handle resolution, `status`/`ps --id` dead ends, and profile precedence. What is still live is different. (1) Claude followup fails "session_expired" mostly because the estate launcher (`estate-harness.py`, outside this repo) re-runs its usage autoselect on `--resume <id>` and can land on an account that does not hold the session; Delegate then mislabels that as a lost session and tells the caller to "relaunch with --resumable". (2) Native-session followup is opt-in at launch and nothing at launch, at refusal, or on `resume` lets a caller recover the continuity they needed. (3) `resume`/`followup` swallow options after the handle as prompt text, with the warning surfacing only at the end of a blocking run. Defaulting Codex/Claude work Runs to resumable, plus pinning the account on `--resume`, removes most of the Claude and "not discoverable" cuts. The rest are small hint or default gaps.

## Root causes

### RC-1: Claude `--resume` is not pinned to the account that holds the session (and Delegate misreports it)
- Symptoms: pc2_f1de69234abf7ebe (09-25), pc2_a9ebf93a7b209f99 (09-27), pc2_e5a9d54a671496fe (09-27), pc2_b53e540cf23a3c4f (09-28), pc2_c9f85b036bb52c31 (09-28), pc2_e85dd6fa13b8f225 (09-26), pc2_3a87e81b55e3c7bf (09-28). 7 cuts, all open, all devbox except e85dd6fa.
- Evidence, verified: on the devbox (`ssh devagent`, read-only) I opened stderr.log for three failed followups. Loom del_20260927T035111Z_2c8967 printed `usage autoselect: work-a ... over work-c` then `No conversation found with session ID f0fadc87...`; its source run del_20260927T032601Z_da988c had run on `work-d`. Loom del_20260927T200512Z_ca1cc8 printed `work-b ... over work-d`, its source had run on `work-d`. Fleet del_20260925T175830Z_8e152b failed identically. In `linux-devbox/40-cells/user-env/estate-harness.py`, `maybe_select_best_claude_account` (line ~2629) receives `vendor_args` but uses it only via `_claude_launch_prior` (a load weight, ~2597/2707). Nothing picks the account whose projects dir holds the `--resume` target. `claude_resume_recorded_model` (~2748) does parse the target but only reads `~/.claude/projects` for a model warning. The sibling lane whose followup "worked" in e5a9d54a and b53e540c is what random re-selection predicts (inferred).
- Delegate side, verified: `child_failures.classify_followup_session_failure` (child_failures.py:130-146) maps any "No conversation found" text to `session_expired`, message "no longer available; relaunch with --resumable". The runs in these cuts WERE resumable. The message sends the caller to the wrong fix (and outcome.py:87 maps it to `session_lost`). `followup_command.py` records no account and passes none: the Claude account is chosen after Delegate execs the child, so Delegate cannot pin it today.
- Still live at 0.31.0?: yes (both halves). Cuts e85dd6fa/3a87e81b are the same mechanism through a workflow structured retry: `workflows/runtime.py:4454-4462` picks strategy `resume` whenever the child has a session id, and there is no fallback to `relaunch` when the resume itself fails with session-not-found.
- Why it keeps recurring: account selection lives in a different repo than the code that decides to resume, and the two share no contract. The wrapper treats `--resume` as an ordinary launch.
- Recommended fix: in `estate-harness.py`, when vendor args carry `-r/--resume <id>` (or `--resume=<id>`), find the account dir with `projects/*/<id>.jsonl` and stay on it (skip autoselect; if none holds it, say so and fail fast with a distinct message). Test: two fake account dirs, session under the non-selected one, assert the resolved `CLAUDE_CONFIG_DIR`; this fails today. In this repo, change the followup classifier to say "session not found on the selected account; the Run was resumable" when the source manifest has `resumable: true`, and have the workflow retry fall back to `relaunch` once on a session-missing resume failure.
- Alternative: Delegate records the account label from the `usage autoselect:` stderr line into the manifest and sends it back as an env pin on followup. That works without touching the wrapper but parses free text and couples the repos more. Automatic `followup` -> `resume` fallback (c9f85b03's idea) is a fine band-aid but drops native context, which is the reason followup exists.
- Related: no open bead. The wrapper fix belongs to the linux-devbox repo (`docs/plans/2026-09-25-claude-autoselect-v2.md` is the autoselect design; it does not mention resume).

### RC-2: Native-session continuity is a launch-time opt-in that nothing surfaces or lets you recover
- Symptoms: pc2_9b59c000f14d3364 (08-27), pc2_f3ec31063fc3a90b (08-30), pc2_98bd905637468a42 (09-03, resolved), pc2_436de5a2b1cb2d3a (09-20), pc2_6b78743ddbf5d898 (09-21), pc2_1c6479349b397178 (09-16), part of pc2_919fed47004aa56e (09-16). 7 cuts, 5 open.
- Evidence, verified: `--resumable` is the only thing that keeps the session (Codex adds `--ephemeral` and Claude adds `--no-session-persistence` unless it or `resume_session_id` is set: argv_builders.py:770-779 and :409-420). `followup_command.py:340-354` refuses with `session-missing ... relaunch with --resumable`, which cannot help a run that already ended, and the "relaunch" is a whole new lane. `resume` has no `--resumable` option; `resume_command.py:875-881` only inherits it from the source manifest, so resuming a non-resumable run yields another non-resumable run (1c647934). The skill (`~/.claude-shared/skills/delegate-agent/SKILL.md` lines ~234, 266) and `agent-help` now say to pass `--resumable` and that it is codex/claude only, so 98bd9056 is fixed in text; launch output itself still says nothing about whether the Run can be followed up.
- Still live at 0.31.0?: yes. I found no recorded ruling for opt-in in `docs/plans/deferred.md`, `internal/DEFERRED.md`, or the 2026-07-30 grill doc; it dates from the original followup design (T2).
- Why it keeps recurring: the cost of resumability is decided when nobody knows yet whether a review round will happen. The default protects a storage/privacy property (session files persisted in the native store), but the failure lands on the coordinator, later.
- Recommended fix: make Codex and Claude work-mode Runs resumable by default, with `--no-resumable` (or config `resumable: false`) as the opt-out. One default in request/argv building; keep the current rejection for safe/call/other engines. Sequence it after RC-1, since more followups will hit the account bug. Test: default `delegate codex work` argv contains no `--ephemeral`, manifest has `resumable: true`, and followup resolves a session id.
- Alternative: keep opt-in but print `followup: unavailable (launched without --resumable)` in the launch envelope and give `resume` a `--resumable` flag. Cheaper, no storage change, but still costs a rewritten brief in the 436de5a2 case.
- Related: none in beads. This is a product decision, see open questions.

### RC-3: `resume`/`followup` grammar treats everything after the handle as prompt text, and the only guard speaks at the end
- Symptoms: pc2_9b060733992ac08c (09-07, resolved), pc2_270d16e2ee9d6482 (09-16, open), pc2_919fed47004aa56e (09-16, open; `followup --model/--progress` rejected).
- Evidence, verified by running `parse_cli`: `resume codex-1 --model sol --dry-run` gives `dry_run=False`, prompt parts `['--model','sol','--dry-run']`, and two "option after the prompt is treated as prompt text" warnings. `followup codex-1 --dry-run --prompt-file x` now works (options before the first prompt token are parsed, cli_parser.py:1856-1930), so 9b060733's exact repro is fixed; `followup codex-1 fix it --dry-run` still launches for real. The warning (commit e563b7b0, 09-07) travels on the Request and is printed only in the final result (cli.py:1210-1217, 1279), i.e. after the blocking child ends. `resume` accepts no options after the handle by design (cli_parser.py:1628 docstring), and `followup` deliberately rejects route options (`_followup_inherited_route_message`), which is what 919fed47 hit.
- Still live at 0.31.0?: partly. The silent case became a late warning; a mistyped `--dry-run` still spends money.
- Why it keeps recurring: free-form prompt tail plus option grammar, decided by position. The parser cannot tell a flag typo from prompt prose.
- Recommended fix: for `resume`/`followup`, refuse (exit 2, `option_after_handle`) when a tail token exactly matches a known resume/followup option, unless the caller used an explicit `--`. Prose stays prose because only exact known flags trip it. Test: the two `parse_cli` repros above, asserting a `DelegateError`. This turns the shipped warning into a gate; the `--` escape already exists.
- Alternative: keep the warning but print it to stderr at launch, before the child starts (cheapest; does not stop the spend).
- Related: none open. Same class as the launch-parser tail rule already fixed for `--model` (deferred.md "Per-run model selection").

### RC-4: Inspection defaults serve post-mortems, not polling, and some surfaces overstate certainty
- Symptoms: pc2_0a6558e4291dad6a (`wait --json` timeout dumps ~28k tokens), pc2_c6e9b63aea0fe867 (OMP `current` shown stale on a 429), pc2_485bd8481b65d809 (resultQuality=empty though stdout held a full report), pc2_8859ecd928db2ac9 (run-output `--tail` counts JSONL events; resolved), pc2_da1acd52a34836d9/pc2_3089d2a8067d5229 (status/ps dead ends), and bead dlg-au9. 8 cuts.
- Evidence, verified: `wait --json` builds each run from `_terminal_payload` -> `_merged_view` (full snapshot including `recentEvents`), and only `--structural` trims it (wait_cancel_commands.py:163-200, 362-380), even when the wait timed out and nothing is terminal. `run-output --tail N` is line-based on JSONL stdout; `--max-chars` (default 60000) is the real bound. `status` and `ps --id` are fixed: both now print "use snapshot HANDLE / run-output HANDLE" (I ran them). `runs show codex-1` is not: it returns the generic `unknown_option: runs does not support option: show` with `nextActions: ["delegate help"]`. `_runs_unknown_token_error` (cli_parser.py:2594-2609) hints only for option guesses and handle-shaped tokens, and "show" is neither. That is dlg-au9, still live.
- Inferred/could not determine: the 09-17 stale `current` report. Code inspection shows pi/omp `text_delta` and `message_end` (harness_events.py:1623-1690) and tool starts do overwrite `current`, so the fallback phase in that run must have emitted none of them; I cannot tell which from code alone. The 09-20 `resultQuality=empty` case was a Codex work Run; Codex is deliberately excluded from assistant-message recovery (harness_events.py:217-226, only a message sealed by `turn.completed` counts). The 09-24 outcome-contract commit 2f7fb0e5 (dlg-5kl) postdates the cut and I could not verify it closes it.
- Still live at 0.31.0?: yes for `wait --json` default and `runs show`; partly for the rest.
- Recommended fix: (a) on wait timeout, emit the structural shape by default and keep the full merge for terminal runs only, leaving `--full` to opt in; (b) extend `_runs_unknown_token_error` with a small verb set (`show`, `status`, `get`, `info`, `view`) and point at `run-output HANDLE --completion-report`, which closes dlg-au9 without adding a `runs show` verb; (c) for `resultQuality=empty` with non-empty stdout, name `delegate run-output HANDLE --stdout` in the warning. Tests assert each exact message/payload shape.
- Alternative for dlg-au9: add `runs show HANDLE` as an alias of `snapshot`. It matches `runs prune` grammar but adds a second way to do one thing.
- Related: dlg-au9 (P3 open).

### RC-5: the Registry is per-workspace and only some entry points say so
- Symptoms: pc_d1a5192425bc, pc_fafefc3f7eb3, pc_d55fa4c623b6, pc2_9338d0de891c6aeb, pc2_a17cd7f67c135769, pc2_5d6276cd10767524, pc2_c12ca4bfd653a43c, pc2_7791024cd4c3e523, workflow_not_found x4 (pc2_35eb2278aad4560f, pc2_edcf3e9d7deedcaf, pc2_8c9674c780984f39, pc2_9022287dc3e88422), pc2_f23f74c7ab951305. About 14 cuts.
- Evidence, verified: `runs` reports `total`/`truncated` and a workspace-scoped warning when empty (inspection_commands.py:279-296, commit 3f20035c, 08-10); the main worktree also folds in linked worktrees' registries (`linked_registry_roots`, 09-24). `unknown_handle` names `--cwd`. Bare harness handles warn as `bare_handle_stale`/`bare_handle_ambiguous` (a1d9defb 07-16, 5602edce 08-31), and workflow_not_found now names the searched root (`_workflow_state_hint`, 0f7ff641 09-22).
- Still live at 0.31.0?: partly. Remaining gaps I verified: (1) a relative `--prompt-file` resolves against the process cwd, not `--cwd` (request_build.py:465-469, message shows only the relative path) - f23f74c7; (2) the fold-in is one-directional: main sees linked worktrees, but a linked worktree cannot see the main Registry, and the workflow lookup does no sibling search; (3) the bare-handle stale warning needs age over 24h, so a wrong-workspace pick under a day old is silent.
- Why it keeps recurring: `--cwd` selects both Registry and execution root, but shells and background jobs carry an ambient cwd, so lookups silently follow the shell.
- Recommended fix: resolve `--prompt-file` against the resolved workspace when `--cwd` is given (error names both candidates), and let `unknown_handle`/`workflow_not_found` list sibling worktrees' Registries when the repo has any (reuse `linked_registry_roots`). Tests: launch with `--cwd DIR` and a relative prompt file inside DIR; lookup from a linked worktree of a run recorded in main.
- Alternative: leave as is; hints exist and most cuts predate them.
- Related: none open. `--cwd` stale-wording item pc2_7e38e15c5ac49fa1 is fixed in docs/delegate-workflows.md:333-337.

### RC-6: launch is a foreground supervisor, and killing it takes the run with it
- Symptoms: pc2_d61a04fb736cfb11, pc2_12f89ed4795f7cdc (08-20, open), pc_86b19f593cf1 (08-11, open), pc2_729e4a1e2897c78e (resolved).
- Evidence, verified: the skill now says "A launch command blocks until the child finishes (there is no detach flag)" (SKILL.md:223) and to use the harness background path. In the runner, child stdout/stderr are PIPEs read by the launcher (runner.py:2464-2466), and the child is in its own session (`start_new_session=True`, :2467); `stale` is decided by the recorded child pid being dead (run_status.py:113-124). That a killed launcher leaves a child that dies on a closed pipe and then reads `stale` is inferred; I did not reproduce it (no real lanes allowed).
- Still live at 0.31.0?: yes as a design; the documentation half is done.
- Recommended fix: none needed for the docs half. If Trey wants it, a real `--detach` needs a supervisor process that owns the pipes (as `workflow run` already does), not a shell `&`.
- Alternative: keep foreground and document "killing the launcher cancels the run" in the CLI reference (the skill covers the blocking half but I did not find the kill half).
