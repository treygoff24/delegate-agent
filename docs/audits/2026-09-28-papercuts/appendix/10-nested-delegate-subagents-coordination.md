# F10: Nested delegate refusal, native subagent spawn, datetime.UTC crash, coordinator instructions to lanes

## Bottom line
The biggest cluster (about 89 cuts, 07-19 to 07-22, one benchmark/E2E session, sub-themes 1.12 and 2.0) is not a Delegate defect. Delegate has no nested-call guard at all. The refusal ("bench delegation policy refused nested delegate call") came from a PATH shim written by the personal-agent-benchmark harness (`bench/runner.py`), and its `datetime.UTC` crash (sub-theme 2.1) was in that same shim. Both were fixed in the benchmark repo on 2026-07-26 (commit 0f39408 there), and no cut in the family postdates 07-22. What is still live inside delegate-agent is smaller: (1) the tracked entrypoints crash with a raw ImportError under Python 3.9, and the launcher fix exists only in an untracked, diverged local fork; (2) Codex children launched with `--ephemeral` by default probably cannot fork thread context for `spawn_agent`, and the docs blame the wrong harness; (3) coordinator rulings reach a lane only at its next Stop-hook boundary, and Delegate cannot enforce a "no Beads writes" scope. The mail-send `ok:true` on zero deliveries is already fixed (2026-09-24).

## Root causes

### RC-1: The "nested delegate refused" wall was the benchmark's own blanket shim (one incident, about 89 cuts)
- Symptoms: sub-theme 1.12 (46 cuts, pc_e93ae00a0be8 .. pc_aa342e3b1148) and sub-theme 2.0 (about 43 cuts, pc_8aa6dfc1aec9 .. pc_14de8b2b3bbf, plus pc_0feb0f002f73 which is a different request: a self-check command). Dates 2026-07-19 22:37 to 07-21 19:41, all marked resolved. Treat as one incident. pc_f17838edf01e (inherited DELEGATE_SOURCE_ROOT) is misfiled here; see below.
- Evidence (verified): `grep` across `src/`, `bin/`, `docs/`, `tests/` finds no refusal string and no nested-call guard in delegate-agent. The only nested-invocation logic is `DELEGATE_WORKFLOW_PIN` inheritance (workflows/runtime.py:5237), which is the opposite of a refusal. The shim is generated by `_install_delegation_shim` in `/Users/treygoff/Code/personal-agent-benchmark/bench/runner.py:242`. Before 2026-07-26 it refused every invocation. Commit 0f39408 ("bench: allow read-only delegate probes") added `_READ_ONLY_DELEGATE_COMMANDS` (describe, help, models, profiles, ps, run-output, runs, snapshot, status, agent-help) and `--help/--version/-V/-h`, made `--json` refusals emit a structured `{"ok": false, "error": "bench_nested_delegation_refused", ...}` with exit 1 (fixing pc_566cc3ff255d's jq-masking complaint), and rewrote the message to say "Delegate is installed and working -- this is harness policy" and to point at `.delegate/runs/<run-id>/manifest.json`. The code comment there states the reasoning: read-only commands cannot spawn a nested agent, so refusing them only left contestants unable to tell policy from a broken install.
- Still live at 0.31.0?: No, as a delegate-agent matter. Fixed in the benchmark repo. Not verified: I did not run the shim end to end or the bench tests; I read the source. The benchmark working tree is dirty, but `bench/runner.py` is committed and unmodified.
- Why it recurs: the benchmark task fixture told contestants to "run a Codex e2e" while the harness forbade the delegate CLI, so every contestant tried a harmless probe, hit the wall, and filed a cut. Each attempt was a fresh agent with no memory of the previous 40 identical cuts. The ledger marked them "resolved" per-cut without a code owner ever being named.
- Recommended fix: none in delegate-agent for the refusal itself. Two small in-repo things follow from the cuts' good ideas. (a) Add `DELEGATE_RUN_ID`/`DELEGATE_MAIL_SELF` to `describe_payload.py`'s `childEnvironment` block (line ~1112; today it lists only SOURCE_ROOT, EXECUTION_ROOT, WORKSPACE_ROOT), since a child can use them to know it is inside a Run. These are set only for work runs with mail (`mail_core.bind_mail_identity`, mail_core.py:283). (b) Optionally have the benchmark's task prompt say "the active run is the E2E subject; verify via manifest.json".
- Alternative: add a Delegate-owned "am I nested" marker (`DELEGATE_NESTED=1`) for all harnesses. Rejected as the pick: it duplicates `DELEGATE_RUN_ID`, and only launch attempts need refusing, which is the benchmark's policy, not Delegate's.
- Related: pc_a2a281c8e782, pc_c330a38a7dd1, pc_69d6315f71a4 (cannot tell shim from broken install) are exactly what the new message addresses. No open bead; no deferred-backlog ruling covers this.

### RC-2: Tracked entrypoints have no Python-version guard; the launcher fix lives only in an untracked fork
- Symptoms: sub-theme 2.1 (16 cuts, 07-20 23:48 to 07-22 14:04, all resolved). Two distinct crashes were mixed together: the benchmark shim's own `datetime.UTC` (pc_7d7d32953179, pc_0f7ca2164fb0, pc_5bc949d93b0d, pc_8f5bd9037edd, pc_6d9d6b9ebe8b, pc_0aa0f56e334c, pc_e750b6c8bb1a, pc_6fccc9e7ecfc, pc_9750dacc3299, pc_06f284e6fa20, pc_389d00d7aed3) and the installed launcher on Xcode Python 3.9 (pc_6ca636b93ada, pc_2fa6f73b608e). pc_a0d8cbe5c0ab is a correction note, not a failure.
- Evidence (verified): the shim now uses `datetime.datetime.now(datetime.timezone.utc)` (personal-agent-benchmark bench/runner.py:348), so the benchmark half is fixed. The live launcher `~/.local/bin/delegate` (mtime Sep 11) now has `_delegate_python()` (lines 207-238) that scans python3, python3.14 .. 3.11, and Homebrew for a 3.11+ interpreter, honours `DELEGATE_PYTHON`, and prints a clear error with exit 78. But the tracked template `bin/delegate-profile-shim` contains no such picker (0 matches for `_delegate_python`), and `.claude/skills/install-local/SKILL.md:69` confirms the live launcher is "a diverged, customized fork". The other entrypoints are unguarded: `bin/delegate.py` has shebang `#!/usr/bin/env python3` and does no version check. Running `/usr/bin/python3 bin/delegate.py --version` (Python 3.9.6) fails with `ImportError: cannot import name 'TypeAlias' from 'typing'` from `json_types.py:3`, not even a `datetime.UTC` message. `~/.delegate/bin/delegate.py` is the same file. `pyproject.toml` declares `requires-python >=3.11`, which protects only `pip install`.
- Still live at 0.31.0?: Partly. The interactive launcher path is fixed locally. The repo's own `bin/delegate.py`, the tracked shim template, and any install re-created from the template still produce a raw ImportError on 3.9.
- Why it recurs: the version requirement is enforced at three different places (pip metadata, an untracked launcher, nowhere), and the only guard is in the copy nobody versions. A stripped-PATH context (cron, benchmark sandbox, some agent envs) resolves `python3` to `/usr/bin/python3` = 3.9.6 (verified here).
- Recommended fix: put a four-line guard at the very top of `bin/delegate.py` and at the top of `delegate_agent/__init__.py` (before any 3.11-only import): `if sys.version_info < (3, 11): sys.exit("delegate needs Python 3.11+ (found X); set DELEGATE_PYTHON ...")`. This covers `bin/delegate.py`, `python -m delegate_agent.cli`, and the `~/.delegate` copy regardless of the launcher. Port the `_delegate_python` picker into `bin/delegate-profile-shim` so the tracked template stops being a regression risk. Proof: a unit test that runs a 3.9 interpreter (skip if absent) or monkeypatches `sys.version_info` and asserts the friendly message and nonzero exit; it fails today with the raw ImportError. Check `python3 -c` on the file with `from __future__ import annotations` first, since the guard must sit before the failing import.
- Alternative: leave code alone and rely on the launcher fork. Cheap, but the next fresh install or `install-local` from the template silently reintroduces the cut.
- Related: none open in beads. Not in either deferred backlog.

### RC-3: Codex children are launched `--ephemeral` by default, and the docs blame the wrong harness for `spawn_agent` "no thread with id"
- Symptoms: sub-themes 1.2 and 2.7, 13 cuts, 07-10 to 08-04: pc_08099f2644cd, pc_4a608dca0dec, pc_663e44ffd593, pc_eba615a3b783 (open), pc_2814d3a5c226 (open), pc_5a32e6b4564e (open), pc_23413f2a4d58, pc_b458a3b32b42 (open), pc_aeb4d781768c (open), pc_a9ed7fe40773 (open), pc_b44e9ce19664, pc_16fbbea8b480, pc_ba42bd86f746, pc_ddd587e96c8e. All say Codex `collaboration.spawn_agent`; one (pc_16fbbea8b480) says it fails specifically with `fork_turns=all`.
- Evidence: verified: `argv_builders.py:773-780` appends `--ephemeral` to Codex JSON-streaming runs unless the run is persistent/resumable or `codex.ephemeral` is false (default `True`, config.py:182, docs/configuration.md:420). `docs/plans/2026-07-30-big-three-design-grill.md:10` records this as a deliberate posture. Verified: the installed Codex binary contains the string `no thread with id:` and a `ThreadForkParams` with an `ephemeral` field; it also carries "ephemeral thread does not support goals / thread goals require a persisted thread". Inferred, not proven: that forking a parent thread that was never persisted is what returns "no thread with id". I did not launch Codex to test it.
- Still live at 0.31.0?: Probably yes for `fork_turns=all` in default (ephemeral) Codex Runs; no cut after 08-04, and the documented workaround (`fork_turns: none`) was added 2026-08-10. `docs/troubleshooting.md:570-574` says it is a "Claude Code harness bug ... Not a delegate defect". That attribution contradicts every cut, which name Codex. Unverified beyond that.
- Why it keeps recurring: the skills and briefs the child follows (post-implementation review, research, fleet) mandate a subagent, Delegate never tells the child its session is ephemeral, and the failure surfaces only after the child has decided to depend on it.
- Recommended fix: first run the cheap discriminating test (same `spawn_agent fork_turns=all` prompt via `codex exec` with and without `--ephemeral`; one small paid probe, so it needs Trey's go). If confirmed: correct the troubleshooting entry to "Codex ephemeral session"; tell the operator how to opt in (`codex.ephemeral: false` in config, or make a run resumable); and consider letting a launch flag say "this Run needs native subagents" that drops `--ephemeral`. If not confirmed, still fix the doc attribution.
- Alternative: append one line to the Codex prompt suffix ("native subagent fork may be unavailable; use `fork_turns: none`"). Cheap, works without knowing the cause, but adds prompt text to every Codex Run for an inferred issue.
- Related: the design-grill deliberately kept ephemeral posture (Trey ruling 2026-07-30 covers session resume, not subagents). No open bead.

### RC-4: Coordinator rulings reach a lane only at its own Stop-hook boundary; Delegate has no acknowledgement or ordering contract
- Symptoms: pc2_27a3c079bf28ec95 (lanes miss corrections that arrive mid-work), pc2_d9607f8f6bc91d6d and pc2_d77c8bdd9927edf2 (sends to a finished parent alias silently reached nobody). All open, 2026-09-16.
- Evidence (verified): push delivery exists only for Claude and Codex via a Stop hook (`mail_push.py:50-52`, `MAIL_PUSH_ADAPTER_ROWS`; mail_core.py:75-77). It fires when the model ends a turn, so a lane doing implement, gate, commit in one long turn sees mail only afterwards. The pull prompt says only "At a natural boundary, use `delegate mail inbox`" (mail_core.py:78-83), which is what pc2_27a's brief-level "only when blocked" complaint was about. Recipient eligibility is `mode == "work" and status == running` (mail_core.py:549), so a finished parent alias is `skipped_ineligible` by design. For the "ok:true on zero deliveries" cuts (pc2_d9607f8f6bc91d6d, pc2_d77c8bdd9927edf2): fixed. `_require_a_delivery` (mail_core.py:904-925, commit 6d764804, 2026-09-24, dlg-qd1) now raises `mail_not_delivered` with exit 1 and per-recipient outcomes when nobody received the message.
- Still live at 0.31.0?: Partly. Zero-delivery reporting: fixed after the cuts. Not fixed: forwarding from a finished parent alias to its live continuation (nothing in `_recipient_for_alias` follows continuation lineage), and mid-turn delivery (inferred: no hook fires within a turn; not tested).
- Why it recurs: mail is a pull mailbox with push at turn boundaries; the sender cannot require an acknowledgement, and the prompt asks for a check at "a natural boundary" that a lane defines for itself.
- Recommended fix: the two-line prompt change with the highest value: tell lanes to run `delegate mail inbox` immediately before final verification and before any commit, and to name the latest handled message id in the Completion Report. That is a text change to `MAIL_PROMPT_SUFFIX` (mail_core.py:76). Add the continuation-following or a clear "recipient has a live continuation: <alias>" hint in the `mail_not_delivered` `next_actions` if the run registry records a continuation link (not verified). Prove with a test that a send to a completed alias with a running continuation names it.
- Alternative: a "mail required" resident lane that wakes on mail (dlg-dct, P4 idea). Bigger, and it reverses the pull design.
- Related: dlg-dct (resident lanes that wake on mail).

### RC-5: Delegate cannot enforce a child's tool-level write scope (Beads), so "no bd writes" stays a prose rule
- Symptoms: pc2_90bcac540f7ee300 (child38 created/claimed a bead), pc2_0bccc93c99f9a21d (codex-41 created and closed one). Both open, 2026-09-17, both tower repo.
- Evidence (verified): work mode is "edit-capable" and only the harness sandbox limits it (docs/security-model.md:202-222); Delegate controls argv, mode, workspace, and prompt framing, not which CLIs a child may call (security-model.md:60-70). The repo default close instructions (`bd` block in the child's repo CLAUDE.md/AGENTS.md) beat a launch-prompt ban. `bd` has a `--readonly` flag "for worker sandboxes" (`bd --help`) but no environment variable for it (checked the binary for `*_READONLY`; none), so Delegate cannot set it through child env. Inferred: a PATH shim or bd wrapper would work but is not built.
- Still live at 0.31.0?: Yes, by design; no code path enforces it.
- Recommended fix: this is a coordinator-side concern, not a Delegate defect. The enforceable path is on the bd side (an env-driven read-only mode, or a coordinator-provided `bd` wrapper first on PATH for lanes). If Trey wants it in Delegate, the general form is a launch-scoped child PATH shim, which needs a design decision (see questions).
- Alternative: keep it a rule and accept the leakage; the cost in the cuts was minor (one stray bead each).
- Related: none open; matches the "prose prohibition" complaint in the cut itself.
