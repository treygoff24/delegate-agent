# F2: No preflight (auth/quota, advertised model or harness, shim/config breaking launch, Codex overlay warning, websocket/auth deaths, model substitution, false pauses, burst spawn deaths)

## Bottom line
This family is mostly one gap seen from several angles: delegate knows how a lane is configured, not whether it can run, and when a lane dies before any model output it forgets. The failure classifier (`child_failures.py`) only knows Codex-shaped auth and quota text. Cursor "Authentication required", OMP "No API key found", Kimi 402, Codex websocket closes, Codex config rejects, and most broker 403s all fall through as generic `exit_nonzero`. Nothing is persisted after a failure, and no command reports per-realm lane health. The deferred-backlog ruling (no probe on every launch) rules out the obvious "probe before each launch" fix, so the right shape is a small failure-signature table plus remembered known-bad state plus an opt-in health probe. Two items are plain live bugs with one-line fixes: `mail_push.py` injects `-c hooks=true`, which current Codex rejects, and the Codex overlay warning is a machine-state problem that the code correctly reports. About half of the model-routing cuts were fixed after they were filed (09-17 to 09-25).

## Root causes

### RC-1: Pre-model launch failures are unclassified, unremembered, and treated as permanent by nobody
- Symptoms: about 40 cuts. Auth/quota: pc_027e3771dd2e, pc_8ede948a0f68, pc_a38f126735c1, pc_0a06047433a6, pc_750e7260f083, pc_b46fbf69eed3, pc_01825210cce0, pc2_425f7e5df68990d7, pc2_2fcec7f367892bcc, pc2_62f143c5e3bd3436, pc2_113ee007c75d300f, pc2_f9bba61eb81713ba, pc2_808580a191b70263 and the 08-28 to 09-03 personal-realm OMP/Cursor set. Codex work-a: pc2_7abc3d7a8c7e8a17, pc2_8ac245f86fe91f68, pc2_345de9e514b4017c, pc2_e03bc852e8300b47, pc2_617e4134c656c8df. Provider 401/404: pc2_706a686006242198, pc2_dde3319ccdf99763, pc2_9476fae3556669ee. Codex config reject: pc2_e4d3753e011838c2, pc2_9f9020813a880a2c, pc2_a171639f90fb328c. Broker/spawn: pc2_208bf42c1afe1fda, pc2_b8cb46b6b5180500, pc2_6c3707676de54626, pc2_a139811ec20ea00c. Mostly open, 2026-07-16 to 2026-09-28.
- Evidence (verified):
  - I ran `child_failures.classify` on the literal strings from the cuts. It returned None for "Authentication required. Please run agent login first", "No API key found for opencode-go", the Kimi 402 text, "websocket closed by server before response.completed", "invalid type: boolean true, expected struct HooksToml", "uid_unmapped: Broker returned HTTP 403", "principal_not_cell_principal", and "Cannot use this model: grok". It classified only `token_expired`-style text. `_AUTH_PATTERNS` and `_USAGE_PATTERNS` are at `child_failures.py:43-62`. `outcome.py:77-84` maps only `auth_failed` and `binding_not_active` to `provider_auth`. Everything else becomes `exit_nonzero`.
  - `binding_not_active` (`child_failures.py:39-105`, added 236e2361, 08-31) is the one broker signature recognised. The two other 403 variants in the cuts are not.
  - State is remembered only for Codex usage limits: `failover_state.py:16` has `_VALID_TOOLS = frozenset({"codex"})`, and the block is written only on a usage-limit match (`runner.py:3777`). The auto-fallback (`runner.py:3805-3830`) fires on usage limits only, never on auth or websocket failures.
  - Codex "preflight" is file presence: `profiles.py:379-410` checks `auth.json` is readable. I ran `codex login status` under the work-a CODEX_HOME today and it says "Logged in using ChatGPT", the same account the cuts describe as "identity unavailable". Presence is not validity.
  - Workflows have no shared-cause short circuit. `grep -i 'preflight|probe|circuit'` in `workflows/runtime.py` finds none related to lane health, so pc_027e3771dd2e's "all 10 cells failed" is by construction.
  - A cheap probe already exists but its result is discarded: `account_binding.py:14-75` runs `estate-cursor status --format json` (15s timeout) at finalization. It returns None when unauthenticated and the status is never reported. `estate-omp usage` also works read-only (100ms on the Mac).
- Still live at 0.31.0?: Yes for classification and memory. The underlying auth lapses themselves are provisioning, not delegate. Cursor on the devbox and the OMP personal profile now have working state (`estate-cursor status` reports authenticated on both hosts today; `~/.omp/profiles/personal/agent/agent.db` exists), so those cuts are stale as incidents but not as a class.
- Why it recurs: the classifier grew from Codex failures and is keyed on text, not on engine. There is no per-engine "what a dead lane looks like" table, so each new harness failure is a fresh papercut. Failures are also stateless: the second and tenth launch pay the same price. The `2026-07-26` deferred ruling ("catching a quiet removal requires probing every launch") is a ruling about `--version` probes and shaped the design toward lazy checks. Nobody has extended lazy logic to "a prior run already proved this lane is dead."
- Recommended fix: (1) Replace the flat regex list with an engine-keyed signature table in `child_failures.py`: `(engine, pattern) -> (code, persistence: persistent|transient, hint)`. Seed it from the cut strings: Cursor auth, OMP missing key, Kimi 402, Codex websocket-closed, Codex config reject, broker 403 variants. Map new codes in `outcome.py` to existing `provider_auth`/`provider_error` kinds (the closed enum stays closed). (2) Generalise `failover_state.py` from Codex-usage blocks to a per-lane "known-bad until" marker keyed on the same identity scheme, written on any persistent signature. Next launch of that lane refuses fast, names the hint, and offers `--force-launch` (or expires after the existing 30-minute default). (3) Transient signatures (broker 403 race, EPIPE at spawn) get one retry gated by the existing `_retry_is_safe` (`runner.py:3858`, no tool events, workspace unchanged). (4) In workflows, a stage whose first N results share one persistent signature closes its gate, reusing the existing gate short-circuit. Proof: a unit test feeding each cut string through `classify` and asserting a non-None code (red today), a runner test where a fake child prints the Cursor auth line and a second launch refuses without spawning, and a fake-broker test that fails once with `uid_unmapped` and succeeds on retry.
- Alternative: probe live before every launch using `cursor status` and `omp usage`. It gives first-launch protection, but it adds 100ms to 15s per launch and contradicts the deferred ruling's cost reasoning. A middle path is a probe only on the first launch of a lane per realm per session, which is more machinery than the marker.
- Related: deferred.md v0.21.0 block (no probe on every launch, deliberate). dlg-87d (profile-waterfall, blocked) touches `failover_state.py` and would collide with generalising it; sequence with it.

### RC-2: No surface reports which lanes are usable in this realm
- Symptoms: pc2_ade7a1d5692c3aac, pc2_3ce6651291c95299, pc2_ece025f39422e6c2, pc2_4634c54f80a2af7d, pc2_2fcec7f367892bcc, pc2_c8467961b333ba44, pc2_435ea16ee031e54d, pc2_dd9536b77dc0e10b, pc2_7a25266fb9dd1e28, pc2_f1b93e49995d28b3, pc2_4c3ac31abe5cd5ae, pc2_c9984a2185e0f365 (safe mode hiding OMP credentials), pc2_82897a16c36ec50d, pc2_3c38e6c94e6ddee9, pc2_d896fc0bdd9d6fb6, pc2_e670ad129558de27, pc2_a1bcc87c4b69b8d2, pc_2bcb1053cd91. About 18 cuts, 07-29 to 09-03.
- Evidence (verified): `delegate doctor` returned runtime identity plus config warnings only (nothing per harness). `delegate profiles` returned only the env keys of the active profile. `delegate models` shows `binaryMissing`, but that is a PATH/`which` test: on the Mac, `estate-pi` resolves to a shim that prints "pi CLI is not installed at its exact estate path", so it reports `binaryMissing: false` for a lane that cannot run. On the devbox `binaryMissing: true` correctly flags `opencode`, `droid`, `kimi` (pc2_3ce6651291c95299 is answerable there). There is no per-harness disable key (grep of `config.py` for `enabled`/`disabled` finds nothing for harnesses), so a retired droid stays listed while the binary is on PATH (pc2_ece025f39422e6c2). The discovery cache is deliberately lazy: `cache/discovery/default.json` is dated 2026-08-17.
- Still live?: Yes as a class. Individual auth gaps are fixed by hand.
- Why it recurs: three different sources of truth (config aliases, PATH, discovery cache) describe a lane, and none of them touches credentials. Realm-scoped auth lives in estate wrappers (`estate-cursor`, `estate-omp`) that delegate treats as opaque binaries.
- Recommended fix: extend `delegate capabilities refresh` (explicit, already the sanctioned probe) to record a per-harness, per-profile `health` object in the discovery snapshot: `{authState: ok|missing|unknown, checkedAt, via}`, using the two probes that already exist (`<argvPrefix> status --format json` for Cursor, `<omp> usage` for OMP; others record `unknown`, never a guess). Surface it in `delegate models` and `doctor`, and let RC-1's known-bad marker write into the same record so a failed launch and an explicit probe agree. Add a `harnesses.<name>.enabled: false` key so retired lanes disappear. Prove it with a fake `estate-cursor` that prints unauthenticated status and assert `models cursor` shows `authState: missing` plus a launch warning.
- Alternative: document the per-realm lane matrix in `docs/troubleshooting.md` and stop. Cheap and honest, but it goes stale like the cuts did, and it is the "documentation ask" the cuts already tried.
- Related: deferred.md discovery-cache-keyed-on-auth-profile (open design issue); the health record must key on the same context as the cache or it inherits the ping-pong problem described there.

### RC-3: Codex overlay warning: config-global setting, per-CODEX_HOME file (machine state, not a code bug)
- Symptoms: 18 cuts (pc2_77ad72f251d008ff and siblings), all open, 09-25 to 09-28; plus pc2_0779a7fc73e742af (09-18, doctor).
- Evidence (verified): `~/.delegate/config.json` sets `codex.profile = "delegate"` in the shared base file. Only `~/.ai-profiles/accounts/codex/personal/personal-a/delegate.config.toml` exists; it is comment-only ("intentionally inherits this realm's base config"). `work-a` has none, and the devbox has none in either realm. `config.work.json` and `config.personal.json` are per-realm overlays but do not clear `codex.profile`. The warning is `profiles.py:143-164`. The cut wave starts 09-25 because commit 57f3900e (09-24) made launches print it every time (`request_build.py:1750-1763`, `4059-4063`), on purpose, since Codex accepts a missing profile silently.
- Still live?: Yes on both hosts; `delegate doctor` emits it right now.
- Why it recurs: a global setting names a file that exists in one of two realms, and the warning has no severity or de-duplication, so it trains agents to ignore warnings (the cuts say so).
- Recommended fix: state, not code. The overlay is a no-op, so clear `codex.profile` in the base `config.json` on the Mac and in the devbox provisioning source. Side effects to know: `preflight_codex_home` (`profiles.py:403-410`) requires a readable `config.toml` only when `codex.profile` is set, which is a stale legacy coupling (Codex now reads `<name>.config.toml`); and `codex_failover_identity` (`profiles.py:174-180`) embeds the profile name, so clearing it resets any existing usage-limit block file names. Proof is `delegate doctor` returning no overlay warning.
- Alternative: create empty overlays in work-a and both devbox realms via estate provisioning. Keeps the setting available for real overlays later. If the warning must stay for real misconfigurations, emit it once per (CODEX_HOME, profile) per day so a known state stops repeating.
- Related: none open. Commit ce46ce90 (doctor) and 57f3900e (launch print) are the origin.

### RC-4: Served-model identity is reconstructed from strings, and one evidenced path is dead
- Symptoms: pc2_f14f1f8e62c61d1c (open, live). Fixed and stale: pc2_56465c0d1e68e0fc, pc2_2796cc7802dde8b3, pc2_c475c7448a8c0585, pc2_1a416185d5d1f993, pc2_a50f0be7bf8847a5, pc2_9cfef215caa0605e, pc2_2bc44b083ccdbbc4, pc2_6a72ba99a713253c.
- Evidence (verified): `_cursor_pin_matches` (`harness_events.py:518`) prefers the catalog `displayName` via `requested_model_display_name`, but that field is declared (`harness_events.py:660`), read (`runner.py:443`, `harness_events.py:1009`) and set nowhere except a test (`tests/test_harness_events.py:337`). Production therefore always falls back to rebuilding the label from the selector shape. I called `served_model_matches_requested('cursor','grok-4.7-xhigh','Grok 4.7 256K Extra High')` and got False; without "256K" it is True. Catalog labels carry context words ("1M") the reconstruction cannot produce (`cache/discovery/default.json`: "GPT-5.6 Sol 1M Extra High"). The OMP prefix false-pauses were fixed 09-17 (3b4fffb5, dlg-nqv closed; I re-ran the six cut cases: all pass, 158 harness-event tests pass).
- Still live?: Yes for Cursor labels with context words; no for OMP prefix mismatch.
- Recommended fix: populate `requested_model_display_name` from the discovery record when building the accumulator (the design comment at `harness_events.py:484-490` already intends this), and compare labels with the context tokens stripped. Prove it with a test that feeds the 256K label with a catalog display name and fails today.
- Alternative: drop the substitution warning for Cursor entirely since Cursor cannot fall back silently. Simpler, but loses the real signal.
- Related: dlg-6k6 (cosmetic Cursor family warning wording).

### RC-5: Provider fallback is owned by OMP config, and delegate defaults to fungible
- Symptoms: pc2_66230ee016b01e00, pc2_5353b18363e16b53, pc2_328ef6771cb74b14, pc2_b287515d063e0b7f, pc2_325237937ab8027c; also the "subscription-first failover did not kick in" wording in pc2_f9bba61eb81713ba, pc2_808580a191b70263, pc2_113ee007c75d300f.
- Evidence (verified): `~/.omp/profiles/work/agent/config.yml` has `fallbackChains` (Go to Fireworks) and `fallbackRevertPolicy: cooldown-expiry`. Delegate "does not consume modelRoles" (`docs/configuration.md:701`) and has no fallback logic for OMP, so "failover did not kick in" is misattributed to delegate: the chain only helps when a keyed source exists. Continuity defaults to `fungible` (`request_models.py:21`), so a cross-provider swap is a `model_substitution` warning (`runner.py:414-450`), not a stop. `servedProvider` is now in the envelope (2f7fb0e5, 09-24, after pc2_b287515d), so the "envelope reports requested model" half is fixed. An unknown alias still passes through to OMP's fuzzy resolution with a warn-only catalog message (`request_build.py:3553-3577`).
- Still live?: Partly. Visibility fixed; the ability to say "never spend on Fireworks" is not.
- Recommended fix: a Trey decision (see below). If yes, treat a `provider/model` OMP selector with an explicit provider as pinned by default, so a cross-provider swap pauses at first observation (pinned mode already does this correctly after 3b4fffb5). Note the pause happens after the first observed model event, so the metered call may already have started; true prevention needs an OMP-side `fallbackChains` edit.
- Alternative: leave delegate alone and fix the OMP config (remove Fireworks from chains for the no-spend order). This is a band-aid, but it is the only mechanism that prevents rather than reports.

### RC-6: Mail-push injects a Codex flag that current Codex rejects
- Symptoms: pc2_e4d3753e011838c2, pc2_9f9020813a880a2c, pc2_a171639f90fb328c (3 cuts, 09-16 to 09-17, all open).
- Evidence (verified): `mail_push.py:285-286` appends `-c hooks=true`. With Codex 0.157.1 on this Mac, `codex -c hooks=true login status` prints `Error loading configuration: invalid type: boolean true, expected struct HooksToml`. `codex features list` shows `hooks stable true` (already on). `codex --enable hooks login status` and `codex -c features.hooks=true login status` both load cleanly. Tests assert the broken flag (`tests/test_mail_push.py:153`, `test_mail_push_adapters.py:140`, `test_mail_push_seams.py:269`), so they pass against a fake Codex.
- Still live?: Yes; it only affects opt-in `--mail-push` (stop-hook push is opt-in since d0bbe309). I did not run a real launch, so I did not verify the hook actually fires with the corrected flag.
- Recommended fix: replace the pair with `--enable hooks`, or omit it and let the `hooks` feature default carry it. Update the three tests, and add a check that Codex's `features list` reports hooks before injecting. Proof: a test that runs a fake Codex which rejects `-c hooks=<bool>` the way 0.157.1 does.
- Alternative: gate on the Codex version from the discovery record. More precise for older Codex, but I do not know the minimum version where `hooks` became a feature, so the simpler flag swap needs one live launch to confirm.

## Open questions for Trey
1. Should an OMP selector with an explicit `provider/` default to pinned continuity, so silent cross-provider spend pauses instead of warns (RC-5)? It changes the fleet default and only helps after the first observed event; the alternative is to keep fungible and remove Fireworks from OMP `fallbackChains` where you want no-spend.
2. Should a known-bad lane (RC-1 marker) refuse a launch outright, or only warn? Refusing prevents dead fan-outs but can lock out a lane that was fixed by hand; my pick is refuse with an explicit override and a short expiry.
3. Clear `codex.profile` (RC-3) or keep the setting and provision empty overlays? Clearing is simplest; keeping preserves a hook for a real overlay later.
