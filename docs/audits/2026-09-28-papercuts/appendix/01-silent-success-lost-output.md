# F1: Silent success, lost output, and misclassified failures

## Bottom line
Most of the family (roughly 40 of the ~95 cuts) is already fixed by "one outcome contract" (dlg-5kl, commits 2f7fb0e5..2ca14e80, 2026-09-24). Before it, a Run's `status`/`ok`/exit code followed the child's exit code while `terminalState` and `resultQuality` separately said "failed". The installed runtime is an estate-sync of main from 2026-09-27 03:00 (verified: `~/.delegate/src/delegate_agent/outcome.py` exists), so cuts dated before that and about exit-0/no_assistant_text are stale. What is still live is narrower and has three parts. First, Delegate treats the end of the child's turn as the end of the Run and never checks that the last message is a report. Second, failure reasons are recovered by regex over concatenated text and carried verbatim only for pi/omp. Third, the tracked stdout cap is a kill switch and partial output is dropped on every failure path except `cancelled`. The two changes that remove the most pain: put a provider error (status plus message) on the accumulator as a first-class field for every Harness, and stop treating "turn ended" as "Run finished" (child-side instruction plus disable Claude's background tasks).

Note: the ledger marks "resolved" when a fix merged, not when installed (dlg-5kl's close reason says papercut resolutions wait for the publish), and several open cuts (`pc2_531397dd`, `pc2_25bd82ed`, `pc2_13bd21da` in part) predate the fix. Ledger hygiene, not code.

## Root causes

### RC-1: "Succeeded" was derived from the child's exit code; result quality was advisory (FIXED on main and installed)
- Symptoms: about 30 cuts. Sub-theme 1.8 (`pc_c7f83ba0`, `pc_db3e420a`, `pc_6150a9af`), all of 3.0 (`pc2_531397dd`, `pc2_25bd82ed`, `pc2_b5f5c899`, `pc2_6620eb09`, `pc2_f0dfe8e7`, `pc2_8809ae20`, `pc2_5ff59b31`, `pc2_6645c397`), most of 4.6 (`pc2_45852d7b`, `pc2_131d68e2`, `pc2_d2ce700c`), `pc2_ba049c7e` (402 shown as success), `pc2_13350882`. 2026-07-13 to 2026-09-24.
- Evidence (verified): `outcome.py:1-14` docstring describes exactly this split. `compute_outcome` (`outcome.py:167-268`) now fails an exit-0 run for `no_assistant_text`, an unrecovered quota error, a terminal harness `failed`, or a missing `--expect-file`. `runner.py:3369-3383` calls it once. pi/omp `stopReason=error` or HTTP `errorStatus>=400` records a failed terminal (`harness_events.py:1696-1735`). The call path applies the same rules (`runner.py:5598-5627`). `tests/test_outcome_contract.py` plus `tests/test_child_failures.py` pass (37 tests, run here).
- Still live at 0.31.0 (main)?: no for the reported symptoms. Two deliberate residuals are listed under RC-2.
- Why it recurred: four surfaces each computed "ok" their own way (dlg-5kl description), and quality checks were added as warnings rather than inputs to the status.
- Recommended fix: none new. Confirm the ledger resolutions and close the open cuts (`pc2_531397dd`, `pc2_25bd82ed`, `pc2_13bd21da`).
- Related: dlg-5kl (closed). No open bead.

### RC-2: The end of the child's turn is treated as the end of the Run; nothing checks the last message is a report
- Symptoms: all of sub-theme 6.0 (16 cuts, 2026-09-23 to 09-26: `pc2_fa66aa77`, `pc2_c8f83deb`, `pc2_742e11d3`, `pc2_15ab8834`, `pc2_ec5145c8`, `pc2_faa47d54`, `pc2_c2c612f7`, `pc2_67bfd306`, `pc2_bfa1235c`, `pc2_254d3ac7`, `pc2_d169e7cd`, `pc2_1e99ec5e`), plus `pc2_13bd21da` ("Now let me write my report", no file), plus `pc2_b5f5c899` (empty final turn with half-finished edits). Mostly open.
- Evidence (verified): Headless `claude -p` and OMP end when the model stops; background Bash and Monitor tasks die with the session. `prompt_instructions.py:44-59` (`COMPLETION_REPORT_SUFFIX`) says nothing about turn end or background work. Delegate sets no Claude environment (grep for `CLAUDE_CODE` in `src` finds only session-id metadata). The Claude binary on this Mac (2.1.284) contains the string `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` (found with `strings`; its behavior is not tested). The only guard is `_process_group_orphaned` (`runner.py:5023-5048`), a warning-only probe of surviving group members. It does not fire if the harness reaps its own background tasks before exiting (inferred; no run in the local registry carries `orphanedProcesses`, so unproven). "Monitor armed; waiting for both suites to finish." is non-substantive by the repo's own heuristic (`is_substantive_assistant_text` false; checked), but that heuristic only sets `suspect_short` in safe mode (`runner.py:1163-1172`), and `suspect_short` never fails a Run (`harness_events.py:125`). In work mode it is `ok`.
- Second residual (verified, `outcome.py:254-258`): a work Run that exits 0 with no assistant text but changed files is `succeeded` with a warning. That was a deliberate ruling ("so the work can be adopted"). It is exactly the `pc2_b5f5c899` shape (8 of 11 lanes died with half-finished edits), so that cut is now a warning only.
- Still live at 0.31.0?: yes.
- Why it recurs: exit and terminal semantics are per-turn, but the caller's contract is per-task. Delegate has no notion of "the child promised more work". The prompt tells children to write a completion report but not that ending the turn ends the Run.
- Recommended fix, in two parts.
  1. Prevent at the source. Set `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` in the env of headless claude children (first check the flag's semantics against 2.1.284 docs), and add a two-sentence "ending your turn ends the Run; background commands and monitors die with it; run long jobs in the foreground" clause to the tracked-run prompt suffix for every engine. Touches `request_build.py` env assembly and `prompt_instructions.py`.
  2. Detect. Add a `FAILURE_TURN_INCOMPLETE` outcome (or a hard warning first) when a work/safe Run's final message is non-substantive and either `orphanedProcesses` is true or the stream shows an unfinished background tool use (Claude `tool_use` with `run_in_background` or Monitor, no result). Touches `harness_events.py` and `outcome.py`.
  - Proof: a fake claude stream-json child whose last event is a Monitor `tool_use` plus the text "Monitor armed; waiting", exit 0. Against today's code the Run is `succeeded`. Also a test that the child env carries the flag.
- Alternative: prompt clause plus `--expect-file` guidance in the skill only. It is cheap and covers most of the risk, since the briefs already say "foreground", but the cuts show briefs don't hold. Do not make `work_changed` quiet runs fail unless Trey reverses the dlg-5kl ruling (see questions).
- Related: dlg-dct (idea: resident lanes that wake on mail) would remove the need to wait in-turn, but it is a P4 idea. No bead for this.

### RC-3: Provider error identity is recovered by first-match regex on concatenated text, and carried verbatim only for pi/omp
- Symptoms: `pc2_22108b42`, `pc2_ffc0a0ae`, `pc2_4fd5a645`, `pc2_b949bf1b`, `pc2_548f0d71`, `pc2_9ada3094`, `pc2_7735be86`, `pc2_ba049c7e` (402), and the recurring `pc2_d2ce700c` / `pc2_af757816` shape. Mostly open, 2026-08-30 to 09-28.
- Evidence (verified):
  - `runner.py:3334-3341` builds `signal_text` as stderr tail plus every error event of the final attempt; `child_failures.classify` (`child_failures.py:95-124`) returns the first pattern that hits, in fixed order (thread loss, then auth, then usage). An incidental earlier line beats the terminal reason. That is a plausible cause of `pc2_548f0d71` (capacity reported as `codex_thread_lost`), but the actual stream was not available, so this is inferred.
  - The auth regexes are loose (`\b(?:expired|invalid|revoked)\b[^\n]{0,50}\btoken\b`, and `\b401\b`). I confirmed a 400 line containing "invalid ... token" classifies as `auth_failed`. The real `pc2_9ada3094` text was not available, so I cannot say which pattern fired.
  - Patterns miss common billing and gating text. Checked: "402 Insufficient account funds", "Grok Build usage balance exhausted", "flagged for possible cybersecurity risk", "18+ age confirmation required", and "Selected model is at capacity" all return `None`. They land as `child_failed` with `failureKind: exit_nonzero` (`outcome.py:131`).
  - Only pi/omp carry the provider's own words into the envelope: `_unclassified_provider_failure` (`runner.py:5351-5359`) is gated on `harness in {"pi","omp"}`. For codex, grok, cursor, and claude the envelope `message` is the literal "Child command failed." (`runner.py:_failure_details`, line 1193). The reason survives only inside the synthesized report as "Harness error:" (`runner.py:1356-1360`).
  - The synthesized failed report's next action is always `run-output ... --stderr --tail 80` (`runner.py:1338-1343`), even when stderr is empty and the reason is in stdout events (`pc2_b949bf1b`: "reason only visible in run-output").
  - stderrTail (added 2026-08-25, 0c62e4e0) helps only if the child writes to stderr. `pc2_22108b42` and `pc2_ffc0a0ae` (08-30, 08-31) postdate it and still show nothing, so their diagnostics are on stdout or absent. The exact cause is not determinable from the cuts.
  - Sub-theme 1.0 (Codex quota/auth/thread reported as generic `harness_error`, 2026-07-10) is fixed by typed failure codes in 0.20.0 (`CHANGELOG.md:1198`), including redaction of quota text (1288). Those four cuts are stale.
- Still live?: partly. Quota/auth/thread wording and pi/omp errors work. Everything else falls to a generic message.
- Why it recurs: failure identity is inferred from free text instead of captured as structured data. Each new provider phrase is a new regex, and the closed `failureKind` enum has no bucket for "provider request rejected" or "provider gate".
- Recommended fix: add a bounded, redacted `providerError` to `StreamAccumulator` (HTTP status if present, provider code, message, source event). Each parser fills it: pi/omp already see `errorStatus`/`errorMessage` (`harness_events.py:1706-1728`); codex and grok `error` events carry a message (`harness_events.py:889-905`); claude `result` `is_error`. Then (a) put the message in the envelope `message`, `terminalRecord.reason`, and the report for every Harness (generalize `_unclassified_provider_failure`); (b) classify by status first (401 to auth, 402 or 429 to quota, everything else to `provider_error`), keeping regexes as a fallback on the terminal error only; (c) point the next action at whichever of stdout or stderr is non-empty. Touches `harness_events.py`, `child_failures.py`, `runner.py`, `outcome.py`. Proof: fixtures where a codex `error` event says "flagged for possible cybersecurity risk" (exit 1), an omp `turn_end` with `errorStatus 400` and text containing "invalid ... token", and a 402 grok error. Assert envelope `message` carries the provider text and `failureKind` is not `provider_auth` for the 400. Each fails against today's code.
- Alternative: keep regexes and add the missing phrases plus an ordering fix. Cheap and fine for this week, but it repeats the treadmill (five phrase-misses in this family alone). A `provider_exhausted` kind for workflows exists already as `provider_quota` (`on_failure="typed"`, 2f7fb0e5), so `pc2_7735be86` is mostly a classifier-coverage problem for the grok 402 phrasing.
- Deferred rulings: "Verbatim child event text" (raw diagnostic mirrors, composed surfaces redact) permits this, since the new field lives on composed surfaces and must be redacted. "No probe on every launch" (lazy upgrade probe) rules out an age-gate or account-eligibility preflight (`pc2_c1b62cc6`, `pc2_96c42d4e`); the fix above makes the launch failure legible instead.

### RC-4: The tracked stdout cap is a kill switch fed by the same bytes as the parser, and only one record shape is compacted
- Symptoms: sub-theme 6.6 (`pc2_46ca3b05`, `pc2_0ec12721`, `pc2_3aa5f3a8`), `pc2_c49473eb`, `pc2_5793025c`. Open except the last; 2026-09-01 to 09-25.
- Evidence (verified): `_drain_stream` (`runner.py:1618-1638`) writes only captured bytes to the log and calls `on_line` on those same bytes. When `BoundedCapture._retain` exceeds `max_bytes` it raises `CaptureLimit`, the limit signal trips, and the process group is killed (`runner.py:2841-2850`). The only compaction is the exact `thinking_delta` record shape, and only for OMP (`stream_capture.py:36-52`, policy `omp-thinking-v1`; landed 09-05, which fixes `pc2_5793025c`). Grep finds no handling for OMP `tool_execution_update` (only a comment in `stall_watchdog.py:599`), so the sub-agent flood in `pc2_3aa5f3a8` still counts fully. Cursor file-read payloads are also uncompacted. The limit is configurable per engine (`trackedStreamMaxBytes`, `docs/configuration.md:361`), but the failure message (`runner.py:3021-3024`) names the number, not the key.
- Still live?: yes for omp `tool_execution_update` and Cursor.
- Why it recurs: the cap protects disk, but it is implemented by killing the child, and the parser is coupled to the retained bytes, so hitting the disk cap also blinds the accumulator. Each flooding event shape needs its own compaction rule.
- Recommended fix: decouple. Past the cap, stop writing to `stdout.log` (record a truncation marker and `stdoutCapture`), keep feeding the accumulator, and let the Run finish. Keep a large hard ceiling (the existing 256 MiB transport limit) as the kill. Also name `trackedStreamMaxBytes` in the failure message. Touches `stream_capture.py` and `_drain_stream`. Proof: a fake child streaming 20 MiB of bulky tool events then a report; today the Run dies `output_limit_exceeded`, after the fix it succeeds with a truncation warning and the report intact.
- Alternative: add a compaction rule for `tool_execution_update` args and for Cursor tool payloads (the current pattern). Smaller and safe, but reactive. Raising the per-engine config default for Cursor is the band-aid.
- Related: none open.

### RC-5: Partial output is recovered only for `cancelled` Runs; failed Runs and per-turn resets discard it
- Symptoms: `pc2_c49473eb` (no partial report), `pc2_ba049c7e` (report lost, thin summary kept), `pc2_5f431ae8` (in part), `pc2_064504322` (partial report after classifier stop), `pc_d046974e` (a housekeeping final overwrote a full review), `pc2_140ec4c8`. Mostly open.
- Evidence (verified):
  - `_completion_report_text_and_source` (`runner.py:1276-1370`): the cancelled branch quotes recovered child text under "Partial output recovered" (added 08-25, 71a87592, the grok fix); the failed branch (1329-1356) builds a report from message, harness error, and stderr only. Output-limit, stall, timeout, `provider_max_turns`, and refusal Runs are `failed`, so their partial assistant text is missing from `completion-report.md` (still in `stdout.log`).
  - For pi/omp, `_reset_pi_turn_text` (`harness_events.py:1615-1621`) runs at every `turn_start` and clears `completion_text`, `_last_substantive_assistant_text`, and `_last_recoverable_assistant_text`. A long review in one turn followed by a short or empty final turn (for example after failover) leaves nothing for `run-output` to recover. Other Harnesses prefer the last substantive message (`harness_events.py:1939-1941`), so this is an inconsistency. That `pc2_ba049c7e` is this mechanism is inferred, not shown.
- Still live?: yes.
- Why it recurs: "no valid completion report" and "nothing worth showing" got conflated; the 08-25 fix repaired one branch only.
- Recommended fix: in the failed branch, quote the last substantive assistant text (same block as the cancelled branch, `completionReportSource` stays `delegate_synthesized`). For pi/omp, keep the last substantive text across turns instead of clearing it (clear only the completion candidate). Proof: pi fixture turn 1 long review, turn 2 tool call, turn 3 empty; assert the report contains turn 1. A second fixture kills at the cap after text and asserts the failed report includes it.
- Alternative: tell readers to use `run-output --stdout`. Costs nothing but leaves the synthesized report misleading.

### RC-6: pi/omp/opencode token usage is never read from the stream
- Symptoms: `pc_35e84522` (zeros), `pc_8f219a36` (216 attempts lost telemetry). Open, 2026-07-20 and 07-21.
- Evidence (verified): usage is set only for cursor (`harness_events.py:1334-1336`), codex (1407), and grok (1458-1463); `_ingest_pi_event` never reads `message.usage`. The Unreleased entry "tracked runs persist the harness-reported token usage" therefore yields nothing for omp. On the claimed "discarded 4.7 MB raw stream": every tracked run dir keeps `stdout.log` (listing of a real run dir shows `stdout.log`, `events.jsonl`, `state.json`), so I could not reproduce the loss. The consumer probably read the envelope. The all-zero values in `pc_35e84522` are the provider's (also seen in the ox cut, "usage 0"), so inferred: even a correct ingest would show zero on that provider.
- Still live?: yes for the missing ingest.
- Recommended fix: ingest pi/omp `message_end` usage into the accumulator, summed across turns, with `basis: "unavailable"` when all counters are zero (zero is not evidence). Proof: fixture with nonzero `message.usage`; today `state.json.usage` is absent.
- Alternative: document that omp usage is unavailable. Adequate if benchmark tooling is the only consumer.
- Deferred: kimi usage is separately deferred (`internal/DEFERRED.md`, upstream emits none).
