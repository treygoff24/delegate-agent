# F8: CLI surface (flags, help/describe, docs/skill drift, mail syntax, brief limits)

Method note: I ran read-only forms (`--json dry-run ...`, `help`, `describe`, `models`, `runs`, `parse_cli` in-process) on 0.31.0, plus an archived copy of main as of 2026-08-19 (in the scratchpad) to test the "exit 0" cuts. One mistake: `delegate codex work --group X hello` (meant as a placement probe, no `dry-run` prefix) launched a real Run, `codex-1117`, in this checkout (isolation none, prompt "hello", reported no file changes; repo tree still clean). Reported so it can be cleaned from the Registry if wanted.

## Bottom line

Most of the 100-odd cuts in this family are already fixed at 0.31.0 or were never CLI bugs. The Aug 25 commit `0ab477d6` made global options position-agnostic, `misplaced_global_option` no longer exists in `src/`, `ps`/`--tail`/`--prompt-file /dev/stdin`/`mail send -`/`snapshot --cwd` all work, and the skill was patched on 09-28 for `models <engine> --live`. Three things are really still wrong. (1) Placement is still two rules: globals are hoisted from anywhere (which now eats prompt words), while launch options after the prompt silently become prompt text with only a warning. (2) The CLI never exits 0 on usage errors; that whole cluster is pipes, backgrounding and systemd hiding a real rc=2, so the fix is not in the parser. (3) Help, docs and skills are hand-written copies of syntax the parser enforces, and hint tables are grown one papercut at a time, so every fixed dead end is followed by a new guessed word. A parse-only test that runs every documented command line through `parse_cli`, plus one applicability model for options, would remove most of what recurs.

## Root causes

### RC-1: Two placement rules remain: globals hoisted from anywhere, launch options only before the prompt
- Symptoms: pc_92319c59, pc_858dc4a8, pc_31ede047, pc_617f0f93, pc2_64709327, pc_fc69db55, pc2_44711575, pc2_9cc7b1ce, pc2_1d078069, pc_762a0b22, pc_bf02a328, pc_5a597f80 (12 cuts, 07-15 to 08-26; mostly resolved, three open).
- Evidence (verified): `cli_parser.py:76-124` `_normalize_global_options` pulls every token in `GLOBAL_OPTIONS` out of the whole argv before `--`; `_validate_global_options` (`:143`) rejects only by `CommandSpec.unsupported_global_options`. `--json` and `--group` after `work`, `dry-run --json codex ...`, `--effort xhigh` (now `unknown_option`, with rc 2) behave as expected. But the hoist has no notion of "where the prompt starts". `delegate --json dry-run codex safe review the --group flag` succeeds with `group: "flag"` and the prompt truncated to "review the"; `... review the --cwd flag` fails with `invalid_cwd`. Separately, `parse_prompt_tail` (`:2360-2361`, `_absorbed_option_warning`) turns a valid launch option after the prompt into prompt text plus a warning: `dry-run codex work Do the thing --reasoning-effort xhigh` returns ok, warning "option after the prompt is treated as prompt text". That is the same silent default-effort outcome as the "xhigh evening" cut, in its recognized-flag form. `consume_json_option` (`:1133`) is now a redundant compatibility shim called from about 15 parsers.
- Still live at 0.31.0?: partly. Placement errors and dropped unknown flags are fixed; the two hazards above are live (verified by dry-run).
- Why it recurs: the fix chose "forgive globals anywhere" for `--json`/`--group`/`--cwd` but left the launch-option grammar "options, then variadic prompt". A variadic prompt tail cannot also be scanned for flags without either swallowing prose or swallowing flags.
- Recommended fix: one rule everywhere: option tokens are recognized only before the first positional or `--`; after that everything is prompt text and any flag-shaped token in the tail is an error naming `--`, quoting, or `--prompt-file` (the unknown-token branch at `:2329-2343` already does this). Drop the "absorb with warning" path and stop hoisting globals out of the prompt tail (keep `--json` trailing acceptance, since a test pins it, but only when it is the last token). Prove it with a parser test that fails today: `["dry-run","codex","safe","review","the","--group","flag"]` must not set `group` and must not silently shorten the prompt, and `["codex","work","do","it","--reasoning-effort","xhigh"]` must raise.
- Alternative: hoist launch options from the tail too (fully position-agnostic). Simplest mental model, but widens the prose-eating bug to every launch option; only sensible with a `--` requirement for any prompt containing a flag-shaped word.
- Related: `docs/plans/deferred.md` records the earlier "leading `--model X` in a prompt tail is silently swallowed" note (shipped as a warning, not a refusal); this is the same gap. Bead dlg-44w.7 explicitly left the placement policy open (pc2_64709327 "needs a policy call"); 0ab477d6 answered it for globals only.

### RC-2: The "usage errors exit 0" cluster is a masked rc=2, not a CLI defect
- Symptoms: pc2_ec1c7f19, pc2_44711575, pc2_37878486, pc2_8607ba9f, pc_fc69db55, pc2_5dbc2b83, pc2_586b6c7c, pc2_45b8a46b (8 cuts, 08-11 to 09-13; 4 open).
- Evidence (verified): rc=2 today for `codex safe --bogus x`, `--prompt-file /nonexistent` (with and without `--json`), unknown help topic, and through the installed launcher (`~/.local/bin/delegate`, 0.31.0). An archive of main at 2026-08-19 also returns rc=2 for `unknown_option`, `misplaced_global_option` and `prompt_file_not_found`. `emit_error` (`cli.py:1605-1641`) returns `error.exit_code` (default `EXIT_USAGE`); `test_malformed_launch_exits_nonzero` pins it (commit `2663c643` was a test only, no code change). The reported exit 0 came from `| tail`, a backgrounded task whose "completed, exit 0" is the host task status, or systemd. The Bash footgun hook fired on exactly this pattern (`echo $?` after a pipeline) while I worked. `agent-help` already says not to pipe launches through `tail`.
- Still live?: no as a CLI bug. pc2_8607ba9f ("prints the OLD run's completion report plus an error") I could not reproduce (could not determine).
- Why it keeps recurring: a JSON error goes to stdout with empty stderr and an rc that the calling harness discards; the agent's only evidence of failure is text it did not read. Also this was closed twice in the ledger without a diagnosis, so it kept being re-reported.
- Recommended fix: docs and skill only. Close these cuts as "rc is 2; check the pipeline", keep the `agent-help` note, and add the same sentence to the skill Launch step. No code change.
- Alternative (small, optional band-aid): in `--json` mode also print one `code: message` line to stderr on errors, so `> out.json 2> err.log` launches leave a non-empty err file. Cost: a second output channel to keep in sync with the envelope; I would not do it unless the docs fix does not stick.
- Related: dlg-44w.7 (closed) already concluded the same in effect.

### RC-3: Option applicability lives in prose plus late validators, not in the option registry
- Symptoms: pc_493866f6, pc_b14de596, pc_a72279fc, pc2_5dbc2b83, pc2_5f142079, pc_719f6bf6, pc_ecf626fe, pc_3378785e, pc_e3135446, pc_bf02a328, pc_316c87b3 (11 cuts, 07-10 to 07-24; 7 open).
- Evidence (verified): `command_help.OptionSpec` is only `flag, arg, description` (`command_help.py:27-32`). `help codex` prints one option table for `safe`, `work` and `call`, so `--forbid-commit`, `--include-dirty`, `--base`, `--env`, `--setup` all look valid for `safe`; applicability is in prose ("work + persistent worktree only") and enforced later in `request_build.py` (`_validate_include_dirty` at `:1312`, `_validate_forbid_commit` at `:790`). Results today: `dry-run codex safe --include-dirty x` and `--forbid-commit x` fail `invalid_option_combination` (pc_b14de596 still true; safe already mirrors dirty files, so `--include-dirty` is a no-op that could be accepted). `work --forbid-commit` with no isolation is silently promoted to worktree; the disclosure is a `warnings` entry (`note: --forbid-commit implies --isolation worktree`, verified in dry-run). I did not confirm whether a real launch prints it at start rather than only in the final envelope (pc_719f6bf6 says only at the end; could not determine). `--forbid-commit --isolation none` is refused with a "Corrected command" that swaps in `--isolation worktree` (`cli_parser.py:1283-1297`), which changes where the output lands rather than fixing a typo. Fixed already: `run-output --tail` alone now defaults to stdout (pc_e3135446 is stale); `--max-chars` with `--completion-report` is still refused with a generic "add --stdout/--stderr or remove the ignored flag" that never mentions completion reports (pc_ecf626fe/pc_3378785e live).
- Why it recurs: the same rule is written three times (help text, prose note, validator) with no shared source, so every option-by-mode combination is a separate papercut.
- Recommended fix: give `OptionSpec` an `applies_to` (modes, requires isolation lifecycle, mutually exclusive with). Render per-mode usage lines in `help <engine>` from it and let the parser produce the rejection text from it (name the mode, name the flag that would make it valid). Make `--include-dirty` in `safe` a no-op with a note, and print any implied isolation upgrade on stderr before the launch. Prove: a test iterating every `OptionSpec` that asserts help lists it under exactly the modes the validator accepts (fails today for `--include-dirty`/`--forbid-commit` under `safe`).
- Alternative: edit help text only ("work + worktree only" in the option name column). Cheap, fixes the reading half, leaves the drift mechanism. The deferred ruling on call-mode overclaim (resolved in PR #13) took the derived-from-metadata route for `call`; extend that pattern.
- Related: `docs/plans/deferred.md` "call-mode help overclaim" (resolved by deriving from engine metadata). No open bead.

### RC-4: Hint tables are hand-grown per guessed word
- Symptoms: pc_d684efd8, pc_1c1c53c9, pc_1e815977, pc_53bfd1ec, pc_76b65ea5, pc_7ec39666, pc_f567392d, pc_8ed5614f, pc_ddd99b28, pc_a440651e, pc_07bd6ddb, pc_36a6fa7d, pc2_9d4733cd, pc2_3a9077a3, pc2_57db24cb, pc_14fdab78, pc2_208dfd85, pc2_26fb3dca (18 cuts, 07-15 to 09-06).
- Evidence (verified): four separate tables grew after individual cuts: `unknown_subcommand_message` (`cli_parser.py:814`, `show/status/info/logs/output/kill`), `_MAIL_BODY_OPTION_GUESSES` (`:868`), `_RUNS_HANDLE_OPTION_GUESSES` (`:2582`), and the `run-output --full` to `--raw` special case (`:1127`). Most cuts are fixed: `ps` exists, `mail send --body` gets a targeted hint, `mail send -` parses (verified in-process), `models --live` without an engine says "delegate models <engine> --live", `help models` has the engine-required usage line, `runs --summary` works. Still live: `runs show abc` returns a plain "runs does not support option: show" because `show` is not in the guess set (bead dlg-au9 open); `journal` gets no hint; `describe codex` gives `unexpected_argument` with `nextActions: ["delegate help"]` rather than pointing at `help codex` and `models codex`; `models codex --summary` is rejected by design (help notes it).
- Why it recurs: agents guess vocabulary from other tools (`ps`, `show`, `--body`, `--alias`, `--effort`); each guess gets a bespoke hint only after someone logs it.
- Recommended fix: one synonym registry on `CommandSpec`/`OptionSpec` (`aliases`, `guesses` mapping a guessed word to the real form), consumed by `unknown_subcommand_message`, `unknown_option_message` and the mail/runs cases. Generic fallback for an unknown token under a known command: `nextActions` = `help <that command>`. Prove: one table-driven test over the guessed words seen in the ledger (`ps` accepted, `show`, `journal`, `runs show`, `--body`, `--alias`, `--effort`, `describe codex`) asserting each error names a working command.
- Alternative: keep adding entries (the current practice). Each is trivial, but the cost is one failed agent call per new guess.
- Related: dlg-au9 (open, `runs show`).

- Symptoms: pc_7ec39666, pc_f567392d, pc_8ed5614f, pc_ddd99b28, pc_a440651e, pc_36a6fa7d, pc_6dc65f10, pc_316c87b3, pc2_7f28ae4a, pc2_dfa3e33f, pc2_fa6f73dc (11 cuts).

- Recommended fix: a parse-only doc test in `tests/`: extract every fenced or inline `delegate ...` line from `docs/cli-reference.md` (and the skill, when the path exists) and assert `parse_cli` accepts it or that it is on an explicit "invalid example" list. That test fails today against the pre-09-28 skill text (`delegate models --live`). Also rename or fold the discovery tiers: default = overview, `--summary` only if it is genuinely smaller, otherwise drop it.
- Alternative: keep patching the skill on each cut (what happened on 09-28). No mechanism, but skill text is outside this repo, so a repo test can only cover repo docs; this is the honest limit.
- Related: `internal/DEFERRED.md` and `docs/plans/deferred.md` do not cover this.

### RC-6: Notify adapter passes a flag the installed Post CLI rejects
- Symptoms: pc2_9983998980 (1 cut, 09-23, open, major).
- Evidence (verified): `notify.py:141` builds `post send ... --allow-self --body`; installed `post` 0.9.0 answers `error: unexpected argument '--allow-self'` (`invalid_argument`). `test_notify.py:33-37` asserts only the first four argv tokens, and the fake `post` script just echoes argv, so no test can see the drift. The failure degrades to a manifest warning by design, so a room-notified unattended run completes silently.
- Still live?: yes on this Mac.
- Why it recurs: the contract with another tool is asserted against a fake written by the same author.
- Recommended fix: read `post schema` / `post send --help` capability at first use (or pin a minimum version) and drop `--allow-self` when absent; add a contract test skipped unless `post` is on PATH that runs `post send --help` and checks each flag in `notify_argv`. If Post replaced `--allow-self` with something else, use that; I did not find the replacement in `post schema`.
- Alternative: remove the flag and accept the self-send refusal. Worse: the flag was added on purpose (`ba80dd7c`) for the doorbell case.
