## Findings (most severe first)

1. **minor — double terminal on a cancelled stream.** `src/delegate_agent/harness_events.py:829-847` (provider-terminal block) records a terminal with hardcoded `status="failed"` whenever `_provider_terminal_state` classifies an event — including `PROVIDER_CANCELLED`. Two emitters then record a *second*, unguarded terminal:
   - grok: `{"type":"end","stopReason":"cancelled"}` → provider block records `failed` (~:838), then `_ingest_grok_end` (~:1367-1370) records `grok.end/cancelled` with no `terminal_recorded` check.
   - codex: `{"type":"turn.cancelled"}` → provider block records `failed`, then the `turn.cancelled` branch (~:872-875) records `cancelled`, also unguarded.
   Failing input: either line above. Final `terminal_status` ends `cancelled` (second write wins) and the runner maps `provider_terminal_state == PROVIDER_CANCELLED` to cancelled, so the persisted outcome is right — but the event stream carries a spurious `run.completed/failed`, and a concurrent live-state persist (`maybe_persist_running`) can observe the transient `failed`. The `error` and `result` branches already carry the `terminal_recorded` guard; these two do not. Smallest fix: pass `terminal_recorded` into (or check `self.terminal_event is not None` / `provider_terminal_state is not None` before) the `grok.end` cancelled/failed record and the `turn.cancelled` branch, mirroring the `error` branch.

2. **minor — a provider-typed truncated result can still flip to succeeded.** `src/delegate_agent/harness_events.py:1253-1270` (`_ingest_result_event`): the success path (`result` text present, `is_error` not `true`) calls `_record_successful_completion_text` with no `terminal_recorded`/subtype check. Input: `{"type":"result","subtype":"error_max_turns","result":"partial answer"}` (no `is_error`). The provider table classifies `error_max_turns` → failed terminal recorded (~:838), then the result handler overwrites it with a succeeded terminal and sets `completion_text` — a truncated run publishes as clean success. [INFERENCE] Claude documents `is_error: true` on error subtypes, so the shape may never occur live; the sibling case with `is_error` is tested, this one is not. Smallest fix: in the success path, skip the success terminal (keep text as recoverable) when `terminal_recorded` is true or `subtype` starts with `error_`.

3. **minor — omp write-capable *call* mode emits no approval pin.** `src/delegate_agent/argv_builders.py:566-570` (`_build_pi_family_argv`): `--approval-mode yolo` is emitted only for `engine == "omp" and mode == MODE_WORK`; safe and read-only call get the `always-ask` lockdown. A write-level omp call (`delegate omp call` without `--read-only`) gets neither, so an ambient user/project `config.yml` `approvalMode` governs — exactly the silent-downgrade hazard the A5 comment cites for work mode. Failing command: `delegate omp call --cwd <ws> "edit the file"`. Smallest fix: widen the `elif` to `engine == "omp" and (mode == MODE_WORK or (mode == MODE_CALL and not call_read_only))`.

4. **minor — retry merges drop the new per-run diagnostics.** `src/delegate_agent/runner.py:3405-3490` (`_merge_tracked_attempt_captures`): the merged accumulator copies chunks, events, terminals, usage, and `structured_events_seen`, but not `unhandled_event_types` / `unhandled_event_types_truncated` (E10), `malformed_lines` / `malformed_samples` (E3), or `_last_error_message`. Any codex auth-fallback / thread-retry / empty-success-retry run loses the first attempt's unhandled-type tally and malformed-line count — the visibility E10 was built to provide. Failing input: a first attempt emitting `{"type":"vendor_new_event"}` that then triggers a usage-limit fallback. Smallest fix: merge the dicts/counters in `_merge_tracked_attempt_captures` (sum counts, union keys, keep the truncation flag), and add one merge test asserting the tally survives.

5. **minor — codex mail grant flags land after the stdin positional.** `src/delegate_agent/mail_core.py:372-378` (`wire_work_mail_launch.add_flags`): the `engine == "codex" and prompt_transport == "argv"` branch that inserted flags *before* the trailing prompt is now dead (codex is stdin; argv ends with the `-` positional), so codex flags fall through to `updated.extend(flags)` and append **after** `-`: `codex exec … --json - -c sandbox_workspace_write.writable_roots=[…]`. Whether codex's exec parser accepts `-c` after the positional is unverified here (no binary/shell). Smallest fix: drop the dead argv branch and insert codex flags before the trailing `-` (or before `exec`'s positional generally), and probe once with `codex exec -c x=1 --json -` on a codex-equipped machine.

6. **nit — stale error text can label a later failure.** `src/delegate_agent/harness_events.py:1015-1022` (`_terminal_error_reason`): falls back to `self._last_error_message`, which a *recovered* earlier error set and nothing clears on the generic path. A bodiless `turn.failed` after a recovered `{"type":"error","message":"429"}` carries "429" as its reason. Smallest fix: only use the fallback when the payload's own `error` is absent *and* no successful terminal intervened, or accept the current coupling and note it.

7. **nit — `redacted_prompt_argv` redicts positionally, not by flag.** `src/delegate_agent/argv_builders.py:111-121`: unconditionally replaces `argv[-1]`. Correct for every current caller (kimi builder appends the prompt last; mail flags insert before `--prompt`), but a future caller appending any flag after the prompt would redact the wrong token with no error. Smallest fix: locate `--prompt` and redact its value, falling back to the last element only when the flag is absent.
