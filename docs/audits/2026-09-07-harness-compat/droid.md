## BROKEN

- **[B1] `gemini-3.6-flash` reasoning vocabulary invents a `minimal` tier.** delegate: `src/delegate_agent/reasoning.py:54-57` declares `"gemini-3.6-flash": {"supported": ("minimal", "low", "medium", "high"), "default": "high"}`. Harness: the model table row is verbatim `| Gemini 3.6 Flash | `gemini-3.6-flash` | 0.6× | `low`, `medium`, `high` (default) |` — no `minimal` (https://docs.factory.ai/docs/models). delegate accepts the value, stamps it `reasoningCapabilityEvidence: exact`, and emits it to the child. Repro (no paid call):
  ```
  DELEGATE_CONFIG=<cfg with droid.models.flash=gemini-3.6-flash> \
    python3 bin/delegate.py --json dry-run droid work --model flash --reasoning-effort minimal "x"
  # argv: [... '--reasoning-effort', 'minimal', '--model', 'gemini-3.6-flash' ...]
  # resolved: minimal  source: bundled  evidence: exact
  ```
  Smallest fix: drop `"minimal"` from that tuple in `reasoning.py`. The other five droid rows match the docs table exactly (see OK list), so this is a single-row error, not a systemic one.

- **[B2] Custom-model selectors derived from Factory settings are unusable — wrong field name and a missing index.** delegate: `src/delegate_agent/harness_discovery.py:1175-1192` (`parse_droid_settings_models`) reads `item.get("id")` as the selector and, when absent, synthesizes `"custom:" + "-".join(display.split())`. Harness: the BYOK schema has **no `id` field** — a `customModels` entry is `{"model": ..., "displayName": ..., "baseUrl": ..., ...}` — and the selector form is documented as *"use the `custom:` prefix followed by the display name (with spaces replaced by dashes) **and the index**"*, e.g. `droid exec --model "custom:My-Custom-Model-0"` (https://docs.factory.ai/docs/model-independence/byok, https://docs.factory.ai/docs/droid-exec/overview). So the `id` branch never fires against a real settings file, and the fallback always drops the required trailing `-<index>`. Repro:
  ```
  PYTHONPATH=src python3 -c "
  from delegate_agent.harness_discovery import parse_droid_settings_models
  print(parse_droid_settings_models([{'model':'your-model-id','displayName':'My Custom Model','baseUrl':'https://api.provider.com/v1'}]))"
  # {'custom:My-Custom-Model': {'displayName': 'My Custom Model'}}
  # droid expects: custom:My-Custom-Model-0
  ```
  Blast radius is the discovery listing, not the built-in launch path: `merge_droid_settings` lets help-parsed models win on key collision, but the keys never collide because the index differs, so both a valid and a bogus selector are surfaced to the user. Smallest fix: use the array position as the index when synthesizing the selector, and read `displayName` as the only selector source (keep an `id` read only if a real capture proves the field exists).

## LATENT

- **[L1] The entire Droid capture path rides `--output-format stream-json`, which the current headless documentation no longer lists as an output format.** delegate: `src/delegate_agent/argv_builders.py:203-206` appends `["--output-format", "stream-json"]` whenever `stream_capture` is true, which is the default for every safe/work/call run. Harness: the exec overview says *"Droid exec supports three output formats"* and then documents `text`, `json`, and `stream-jsonrpc` — `stream-json` is absent from that section entirely. It survives only in the CLI reference flags table: `` | `-o, --output-format <format>` | Output format (`text`, `json`, `stream-json`, `stream-jsonrpc`) | ``. The sibling **input** mode is explicitly deprecated: *"the older `stream-json` mode is deprecated"* and *"The older `stream-json` input mode still parses but is deprecated and prints a warning."* (https://docs.factory.ai/docs/droid-exec/overview, https://docs.factory.ai/docs/droid-cli/cli-reference). No changelog entry deprecates the output side, and v0.95.0 (2026-04-06) still improved it (*"Exec mode reasoning output - Reasoning events now properly appear in stream-json exec output"*), so it works today. The risk is that delegate's only Droid capture format is the one Factory has stopped documenting.
- **[L2] Droid stream-json has carried `session_id` since CLI v0.22.3, and delegate never reads it.** delegate: `src/delegate_agent/harness_events.py:708-722` (`_capture_session_id`) branches only on `codex`/`claude`/`cursor`/`omp`; there is no droid branch, so `harness_session_id` stays `None` for every Droid run. Harness: changelog v0.22.3 (2026-10-21) reads *"Added session\_id to stream-json output format for better tracking and debugging"*, and the `--output-format json` result object carries `"session_id": "8af22e0a-d222-42c6-8c7e-7a059e391b0b"` (https://docs.factory.ai/docs/changelog/release-notes, https://docs.factory.ai/docs/droid-exec/overview). Consequence: no session provenance is recorded, and the resume gap in S1 cannot be closed until this is.
- **[L3] Model discovery parses a `droid exec --help` section that no published Factory doc shows.** delegate: `harness_discovery.py:1102-1140` requires headings `Available Models` (and optionally `Custom Models` / `Model details`) inside `droid exec --help`, and raises `ValueError("Droid help had no Available Models section")` when the heading is missing, which fails the whole probe. Harness: the published `droid exec --help` excerpt runs from `Usage:` through `-h, --help` with **no** models section (https://docs.factory.ai/docs/droid-exec/overview); the only "Available Models" on the docs site is the standalone page https://docs.factory.ai/docs/models, whose Markdown table format (`| Model | Model ID | Multiplier | Reasoning |`) does not match delegate's two-space-indented row parser. The repo's fixture `tests/fixtures/discovery/droid_help.txt` was committed 2026-07-20 in `5e570f4` and does contain the section, so the format plausibly exists in the real binary — but nothing current confirms it, and a help-text reflow silently disables Droid model discovery. Note the changelog does record one help-text change: v0.22.4 (2026-10-28) *"Fixed --help text - Running droid exec --help was previously giving incorrect info for using droid exec in streaming mode."*
- **[L4] Droid has no canonical `--version` banner pattern, so selector identity rests on a bare `x.y.z` line.** delegate: `harness_discovery.py:85-94` (`_CANONICAL_VERSION_PATTERNS`) has rows for grok, codex, claude, devin, omp, and cursor but none for droid, so `_expected_version` falls through to `_GENERIC_VERSION = ^\d+(?:\.\d+)+...` matched against a whole stripped line (`harness_discovery.py:634-648`). If `droid --version` prints anything branded or decorated (`droid 0.213.0`, `Factory CLI v0.213.0`), no line matches, and an explicitly configured selector returns `fingerprint_mismatch` and refuses to launch. Cannot be settled without the binary; the docs only establish that `-v, --version` exists.
- **[L5] Reasoning-effort coverage is 6 of 48 documented models, and 2 of those 6 are docs-marked deprecated.** delegate: `reasoning.py:41-69` declares droid rows for `claude-opus-4-8`, `claude-sonnet-4-6`, `gpt-5.5`, `gemini-3.6-flash`, `glm-5.1`, `minimax-m2.7`. Harness: the model table lists 48 IDs, and marks `minimax-m2.7`, `kimi-k2.5`, and `glm-5.1` with *"‡Deprecated. MiniMax M2.7, Kimi K2.5 and GLM-5.1 remain available for now and will be removed in a future release."* (https://docs.factory.ai/docs/models). Because `strategy: "model-table"` fails closed, `--reasoning-effort` on any current flagship (`claude-opus-5`, `claude-fable-5.1`, `gpt-5.6-sol`, `grok-4.6`, …) is rejected out of the box unless the binary is installed for discovery or the operator hand-writes `reasoning.capabilities`. Repro:
  ```
  python3 bin/delegate.py --json dry-run droid work --model gemini-3.1-pro-preview --reasoning-effort high "x"
  # {"error": "unsupported_reasoning_effort", ... "has no declared reasoning-effort capability (harness droid, model 'gemini-3.1-pro-preview')"}
  ```
- **[L6] Discovery reads only `~/.factory/settings.json`, ignoring the legacy file Droid still merges.** delegate: `harness_discovery.py:1397-1408` resolves `HOME/.factory/settings.json` and reads `customModels`. Harness: *"Custom models in `~/.factory/config.json` using snake\_case field names (`custom_models`, `base_url`, etc.) are still supported for backwards compatibility. Both files are loaded and merged, with `settings.json` taking priority."* (https://docs.factory.ai/docs/model-independence/byok). An operator whose custom models live only in the legacy file gets an incomplete catalog with no warning. Also unread: `settings.local.json`, which the same page names as a settings source.

## SIMPLIFY

- **[S1] `droid exec` has had native session continuation since v0.19.8; delegate still refuses `--resumable` for droid on the grounds that it does not exist.** delegate: `src/delegate_agent/cli_parser.py:1356` raises `followup-unsupported` with the message *"--resumable is only supported by codex and claude; droid does not support native session resumption."* and `build_droid_argv` (`argv_builders.py:179-219`) takes no `resume_session_id` parameter at all. Harness: `-s, --session-id <id>` — *"Existing session to continue (requires a prompt)"* — plus `--fork <id>` — *"Fork and resume an existing session into a new copy"* — and the worked example `droid exec --session-id <session-id> "continue with next steps"` (https://docs.factory.ai/docs/droid-cli/cli-reference, https://docs.factory.ai/docs/droid-exec/overview). Changelog v0.19.8 (2025-09-30) added exec session support and fixed continuation; v0.92.0 (2026-04-02) added `--fork`. Repro of the current refusal:
  ```
  python3 bin/delegate.py --json dry-run droid work --model reviewer --resumable "x"
  # {"error": "followup-unsupported", "message": "--resumable is only supported by codex and claude; droid does not support native session resumption."}
  ```
  Work needed is additive rather than deletable: capture `session_id` (L2), add a `resume_session_id` parameter emitting `["--session-id", <id>]`, and move droid into the resumable/`STRUCTURED_RESUME_ENGINES` sets. That deletes the special-case refusal at `cli_parser.py:1356` and lets droid use the shared followup and structured-retry paths instead of the correction-prompt fallback in `workflows/runtime.py:2926-2936`.
- **[S2] Work mode jumps straight to `--skip-permissions-unsafe`, skipping the three graded autonomy tiers Factory added for exactly this.** delegate: `argv_builders.py:194-199` emits `--skip-permissions-unsafe` for `MODE_WORK` and for non-read-only `MODE_CALL`; `--auto` appears nowhere in the codebase. Harness: `--auto medium` allows *"trusted package installs, builds, tests, `git commit`, `git checkout`, and `git pull`"* while blocking *"`git push`, sudo commands, production changes, and sensitive or irreversible operations"*, and Factory's own best-practice list says *"Avoid `--skip-permissions-unsafe` unless fully sandboxed"* and *"Favor `--auto low`"* (https://docs.factory.ai/docs/droid-exec/overview). `--auto medium` is a closer match to what delegate work mode actually needs than the unrestricted flag. Note the two are mutually exclusive: *"Cannot be combined with `--auto` flags."*
- **[S3] Droid safe mode is harness-enforced, not merely prompt-enforced, and delegate's own docs understate it.** delegate: `constants.py:145-152` puts droid in `PROMPT_ENFORCED_SAFE_ENGINES` ("safe mode is substantially prompt-enforced"), and `docs/security-model.md:234` says that for the "read-only sandbox (Cursor, Droid, Kimi) the preamble is the only restriction." Harness: with no `--auto` flag, `droid exec` *"starts read-only by default"*, allowing only *"Read-only file inspection, directory listing, process and environment inspection, and git read operations"* and blocking *"File edits, package installs, git writes, system changes, and deployments"*; further, *"If a requested action exceeds the current autonomy level, droid exec stops immediately with a clear error message, returns a non-zero exit code, and performs no partial changes."* (https://docs.factory.ai/docs/droid-exec/overview). This is a documentation correction in delegate's favor, not a safety hole — the current behavior is conservative. The autonomy table does not address network access, so a "no network in safe mode" claim would still be unsupported.
- **[S4] `missing_model` refusal is delegate policy, not a Droid constraint.** delegate: `request_build.py:1984-1998` / `request_build.py:2803-2811` refuses a Droid launch without `--model` or `droid.defaultModel` with *"captured help does not prove that --model may be omitted."* Harness: every worked example on the exec overview omits `-m` (`droid exec "summarize this repository" --output-format json`), and the repo's own help fixture marks `claude-opus-4-8  Opus 4.8 (default)`. Droid resolves a default model itself. Repro: `python3 bin/delegate.py --json dry-run droid safe "x"` against the unedited example config → `{"error": "missing_model"}`. Deleting the guard would let `MODELESS_ENGINES` (`constants.py:100`) become "all engines" and collapse the droid-only positional-model machinery in `request_build.py:1216-1246, 2779-2830` and `cli_parser.py:1306-1316`.
- **[S5] There is still no scriptable model listing to migrate to.** Confirmed absence rather than an opportunity: the CLI command table lists `droid`, `droid exec`, `droid search`/`find`, `droid mcp`, `droid plugin`, `droid computer`, `droid daemon`, `droid update` and **no** `droid models` or `droid config models`. `droid exec --list-tools` lists tools, not models (https://docs.factory.ai/docs/droid-cli/cli-reference). So `model_discovery.py`'s help-scraping approach remains the only option; L3 is a risk to live with, not one to design away.

## OK (verified)

Flags in `build_droid_argv` (`argv_builders.py:179-219`), each matched against the published `droid exec --help` excerpt and the CLI reference flags table:

- `droid exec` as the headless subcommand — *"Execute a single command (non-interactive mode)"*.
- `--cwd <path>` — *"Working directory path"*. Position after `exec` is fine; commander parses options anywhere after the subcommand.
- `--skip-permissions-unsafe` — *"Skip ALL permission checks - allows all permissions (unsafe)"*. Still present, still spelled the same.
- `--model <id>` — long form of `-m, --model <id>`, *"Model ID to use"*.
- `--reasoning-effort <level>` — long form of `-r, --reasoning-effort <level>`, *"Reasoning effort (defaults per model)"*. Valid on `exec`; the `-r` short form is the one overloaded against interactive `--resume`, and delegate uses the long form, so the overload cannot bite.
- `--file <path>` — long form of `-f, --file <path>`, *"Read prompt from file"*. This is delegate's default Droid transport (`promptTransport: "file"` in dry-run output), and `docs/cli-reference.md:157-158` describes it correctly.
- Prompt as a trailing positional — `Arguments: prompt  The prompt to execute`.
- Stdin transport (`PROMPT_TRANSPORT_STDIN`, argv with no prompt token) — supported by the harness: `echo "summarize repo structure" | droid exec`.
- No `--auto` in safe mode → harness default read-only tier (see S3).
- Exit codes — delegate treats non-zero generically, and the harness commits only to *"exits `0` on success and non-zero on failure (permission violation, tool error, unmet objective)"*. No numeric taxonomy exists to miss.
- Result-event ingestion — `harness_events.py:937-949` (`_ingest_result_event`) reads `payload["result"]` as a string and honors `is_error is True`, which matches the documented terminal object `{"type":"result","subtype":"success","is_error":false,"duration_ms":…,"num_turns":1,"result":"…","session_id":"…"}`. The `assistant`/`user`/`tool_call`/`tool_result`/`error` types in the SDK's message taxonomy all reach an existing generic branch in `_ingest_object`; `hook` falls through and is dropped, which is harmless.
- No native structured output for droid — `workflows/runtime.py:3751-3761` returns `None` for every engine but codex and claude, and Droid exposes no `--output-schema`/`--json-schema` flag. Correct by omission.
- Factory settings path `~/.factory/settings.json` and the `customModels` array key (`harness_discovery.py:1399`, `1216`) — both verbatim from the BYOK page.
- `displayName` as a `customModels` field — correct; it is the `id` read that is wrong (B2).
- Bundled catalog IDs `claude-opus-4-8`, `claude-sonnet-4-6`, `gpt-5.5` (`bundled_models.py:21-25`) — all three still present in the current model table, none deprecated.
- Reasoning vocabularies for 5 of the 6 declared models match the docs table exactly: `claude-opus-4-8` = `off, low, medium, high (default), xhigh, max`; `claude-sonnet-4-6` = `off, low, medium, high (default), max`; `gpt-5.5` = `low, medium (default), high, xhigh`; `glm-5.1` = `off, high (default)`; `minimax-m2.7` = `high (default)`.
- Placeholder guard — `request_build.py:1236-1248` catches the shipped `replace-with-` prefixes. `docs/agent-setup.md:143`'s claim that the Droid dry-run returns `unconfigured_model` with the unedited example config is accurate:
  ```
  DELEGATE_CONFIG=config.example.json python3 bin/delegate.py --json dry-run droid safe --model reviewer "x"
  # {"error": "unconfigured_model", "message": "Droid model 'reviewer' is still a placeholder. ..."}
  ```
- Dry-run argv shapes reproduce cleanly for safe / work / call / call --read-only / file / stdin / no-stream (`build_droid_argv` called directly), and `tests/test_harness_discovery.py -k droid` passes (3 passed).

## Could not verify

- **Everything requiring the binary.** `droid` is not installed here (`which droid` → 127), so I could not run `droid --version`, `droid exec --help`, or any capture. That leaves L3 (does `--help` really carry an "Available Models" section?) and L4 (what does the `--version` banner look like?) open. Both are one command each once a binary exists.
- **The actual `--output-format stream-json` wire shape.** No Factory page prints a single line of it. The `--output-format json` terminal object and the TypeScript SDK's message taxonomy are the closest documented analogs, and I treated them as such rather than as proof. delegate's own `tests/fixtures/droid/README.md` is candid about this: the fixtures are *"Synthetic — hand-written, NOT captured from a real `droid` child run… There is no recorded droid stream behind these files."* `tests/fixtures/droid/simple_text.jsonl` pins `{"type":"message","role":"assistant","content":…}` and `{"type":"completion","finalText":…}`, neither of which appears in any Factory schema; they exercise delegate's generic envelope, so the test is not wrong, but nothing in the repo or the docs establishes what Droid actually emits.
- **Whether `-o stream-json` works without a matching `--input-format`.** The CLI reference says of `--input-format` that it *"Must match `--output-format`"*, but delegate never passes `--input-format`, and the constraint reads as scoped to the flag when used. Needs one live invocation to settle.
- **What Droid does with an unsupported reasoning-effort value** (hard error vs. silent clamp). Undocumented on the CLI reference, models page, exec overview, and changelog. This determines whether B1 is a crash or a silent downgrade.
- **Homebrew formula name and the Windows install command** — the install widget's non-default tabs are JS-rendered and did not scrape. The documented paths that did: `curl -fsSL https://app.factory.ai/cli | sh`, npm `@factory/cli` (binary `droid`, auto-update disabled on npm builds), `droid update --version <x>`, and direct binaries under `https://downloads.factory.ai/factory-cli/releases/<version>/<platform>/<arch>/droid`.
- **Whether 0.210.0–0.213.0 changed anything relevant.** npm has them; the changelog page stops at v0.209.0, so those four releases have no published notes.
